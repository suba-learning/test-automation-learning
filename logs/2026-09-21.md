## Topic
fw-01 — Framework anatomy — Attempt 1 of 2

## Learn

**Goal:** Take a flat, single-file pytest script for api-bug-buddy and refactor it in layers so no test file calls `requests` directly.

1. **Start with the ugly-but-working version.**
   Create `test_users.py`:
   ```python
   import requests

   def test_register_user():
       resp = requests.post(
           "http://localhost:3000/api/public/users",
           json={
               "firstName": "Ada",
               "lastName": "Lovelace",
               "email": "ada@example.com",
               "password": "Secret123!",
           },
       )
       assert resp.status_code == 201
   ```
   Run: `pytest test_users.py -v`
   Expected output: `1 passed`.
   Why: this is the baseline every framework refactor starts from — one file, one request, no structure. Notice already that the base URL is hardcoded and repeated logic (headers, base URL) will duplicate the moment you add a second test.

2. **Extract config.**
   Create `config.py`:
   ```python
   BASE_URL = "http://localhost:3000"
   ```
   Update `test_users.py` to `from config import BASE_URL` and use `f"{BASE_URL}/api/public/users"`.
   Run: `pytest test_users.py -v` — still `1 passed`.
   Why: config isolates environment-specific values so later you can swap `BASE_URL` for staging/CI without touching test logic.

3. **Extract an API client.**
   Create `api_client.py`:
   ```python
   import requests
   from config import BASE_URL

   class ApiClient:
       def __init__(self):
           self.session = requests.Session()

       def register_user(self, first_name, last_name, email, password):
           return self.session.post(
               f"{BASE_URL}/api/public/users",
               json={
                   "firstName": first_name,
                   "lastName": last_name,
                   "email": email,
                   "password": password,
               },
           )
   ```
   Update `test_users.py`:
   ```python
   from api_client import ApiClient

   def test_register_user():
       client = ApiClient()
       resp = client.register_user("Ada", "Lovelace", "ada@example.com", "Secret123!")
       assert resp.status_code == 201
   ```
   Run: `pytest test_users.py -v` — `1 passed`.
   Why: this is the requests.Session pattern from the resource on advanced usage — a single Session reuses TCP connections and lets you attach auth headers once, and it's the seam that keeps `requests` out of test files entirely.

4. **Add login and build a fixture for authenticated state.**
   Add to `api_client.py`:
   ```python
   def login(self, email, password):
       return self.session.post(
           f"{BASE_URL}/api/public/users/login",
           json={"email": email, "password": password},
       )

   def get_me(self, token):
       return self.session.get(
           f"{BASE_URL}/api/public/users/me",
           headers={"Authorization": f"Bearer {token}"},
       )
   ```
   Create `conftest.py`:
   ```python
   import pytest
   from api_client import ApiClient

   @pytest.fixture
   def api_client():
       return ApiClient()

   @pytest.fixture
   def auth_token(api_client):
       api_client.register_user("Grace", "Hopper", "grace@example.com", "Secret123!")
       resp = api_client.login("grace@example.com", "Secret123!")
       return resp.json()["token"]
   ```
   Try running a test that uses `auth_token` twice in the same session — expect a `409`/`400` on the second `register_user` call (duplicate email). Fix by generating a unique email per test run, e.g. `import uuid` and `f"grace{uuid.uuid4().hex[:8]}@example.com"` inside the fixture.
   Why: fixtures centralize setup so every test that needs an authenticated user gets one without repeating registration/login boilerplate, and the collision you just hit is exactly why test data must be unique per run — this is the pytest "good practices" idea of isolating test state (see pytest doc on test layout/conftest).

5. **Write a test using the fixture, and confirm no `requests` import remains in the test file.**
   ```python
   def test_get_me(api_client, auth_token):
       resp = api_client.get_me(auth_token)
       assert resp.status_code == 200
       assert resp.json()["email"].startswith("grace")
   ```
   Run: `pytest -v` — both tests pass.
   Run: `grep -rn "import requests" test_*.py` — expect no output.
   Why: this confirms the layering goal — tests express intent (register, login, get profile) while `api_client.py` owns the HTTP mechanics, matching the separation described in pytest's good-practices guide (test code vs. application/support code).

## Task
Extend this into a real layered structure for the **contacts** resource, which the walkthrough never touched, and add a fixtures layer that goes beyond the single `auth_token` fixture:

1. In `api_client.py`, add methods for all six contacts endpoints: `list_contacts`, `create_contact`, `get_contact`, `update_contact` (PUT), `patch_contact`, `delete_contact`. All must accept a token and go through `self.session`.
2. In `conftest.py`, add a fixture `authenticated_client` that returns an object/tuple bundling a logged-in `api_client` + token together, so individual tests stop threading `token` through every call. Then add a fixture `existing_contact` that depends on `authenticated_client`, creates one contact via the API, and yields its id — and tears it down (calls delete) after the test, even if the test fails.
3. Write `test_contacts.py` with at least 4 tests using only these fixtures (no direct `requests` calls, no raw dict-building of the contact payload in the test body — put a `sample_contact_payload` fixture in `conftest.py` for that): create, get-by-id, update via PATCH, delete-then-get-returns-404-or-empty.
4. While writing the PATCH and DELETE tests, you'll hit two of the known bugs (PATCH ignoring `phone` ~50% of the time, DELETE returning 200 with a body instead of 204). Do NOT work around them — instead add a short `# KNOWN BUG` comment above the assertion and either retry-loop or `xfail`/document the flaky behavior so the suite doesn't randomly fail. Explain your choice in a one-paragraph note in `exercises/fw-01/README.md`.
5. Verify the teardown fixture actually deletes: run the full suite twice in a row and confirm no leftover-contact errors or growing state.
