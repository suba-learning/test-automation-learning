## Learn
A test framework's job is to separate *what a test asserts* from *how the system is reached*. When those two things live in the same function, a single endpoint change (a renamed field, a new header) forces edits across dozens of test files. Layering fixes this by giving each concern exactly one home:

- **Config**: base URLs, timeouts, credentials — read once, injected everywhere. Nothing else should hardcode `http://localhost:8000`.
- **API client**: a thin wrapper class (e.g. `ContactsClient`) whose methods are named after operations (`create_contact`, `delete_contact`), not HTTP verbs. It owns the `requests.Session`, so connection pooling, default headers, and retry behavior live in one place instead of being copy-pasted. This is exactly what requests' advanced usage docs describe with `Session` objects — reusing a session across calls instead of calling `requests.get()` fresh each time.
- **Fixtures**: pytest's dependency-injection mechanism for setup/teardown — "give me a client," "give me a contact that already exists," "clean up after this test." Fixtures compose, so a `created_contact` fixture can depend on a `client` fixture, and tests just ask for what they need.
- **Tests**: pure assertions. A test reads like a spec: call the client, check the response. No `requests.post(...)` should ever appear here.

The analogy: think of a restaurant. The menu (tests) states what a dish *should* be. The kitchen (API client) knows *how* to make it — which pans, which oven temperature. The pantry inventory (config) tracks ingredients on hand. A waiter delivering a pre-plated dish (fixtures) means the customer (test) never touches raw ingredients. If the oven changes brand, only the kitchen changes — the menu stays the same.

pytest's own good-practices guide (see resource link) is the canonical reference for how to structure `tests/`, `conftest.py`, and imports so this layering is discoverable and collectible by pytest itself, rather than just a personal convention.

## Task
In `exercises/fw-01/`, build a minimal 4-layer pytest suite against api-bug-buddy's contacts endpoints:

1. `config.py` — reads `BASE_URL` (default `http://localhost:8000`) from an env var.
2. `client.py` — a `ContactsClient` class wrapping a `requests.Session`, with methods `create(payload)`, `get_all(sort=None)`, `patch(id, payload)`, `delete(id)` — each returning the raw `requests.Response`.
3. `conftest.py` — a `client` fixture (session-scoped, builds `ContactsClient` from config) and a `created_contact` fixture (depends on `client`, POSTs a valid contact, yields the response JSON, deletes it afterward).
4. `test_contacts.py` — at least 3 tests, one per layer-violation check: create a contact via `created_contact`, fetch it via `client.get_all()`, patch it via `client.patch()`. None of these test functions may import `requests` or call it directly — grep the file yourself to confirm.

Run the suite against a local api-bug-buddy instance (Buggy Mode is fine — you're testing structure, not asserting away the known bugs) and confirm it collects and runs.
