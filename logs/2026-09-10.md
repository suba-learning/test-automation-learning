## Topic
fw-01: Framework anatomy — Attempt 1 of 2

## Learn
A test framework's job is to keep *what you're testing* separate from *how you talk to the system* and *how you set things up*. Mechanically, that separation happens in layers:

- **Config**: base URL, timeouts, and environment settings live in one place (e.g. a `config.py` or `pytest.ini`/env vars), so tests never hardcode `http://localhost:8000`.
- **API client**: a thin wrapper class around `requests` (or a `requests.Session`) exposes methods like `get_contact(id)` or `create_contact(payload)`. It owns headers, base URL joining, and session reuse — pytest's good-practices guide notes tests should import your code as a package rather than relying on ad hoc paths, and the same discipline applies to your API client: it's a real module, not copy-pasted request calls. The `requests` advanced docs describe `Session` objects, which are the mechanism that lets a client persist cookies/headers across calls instead of each test re-authenticating.
- **Fixtures**: pytest fixtures (in `conftest.py`) construct the client, seed data, and tear it down — tests declare *what they need* as a function parameter, and pytest resolves *how it's built*.
- **Tests**: pure assertions against the client's return values. No `requests.get(...)` ever appears here.

The analogy: think of a restaurant. Config is the menu/price list (facts everyone references). The API client is the kitchen (it knows how to actually cook — talk to the stove/oven, i.e., the network). Fixtures are the waiter (delivers exactly what a table ordered, handles setup/cleanup). Tests are the customers — they just say "I want the soup" (call `client.get_contact(1)`) and judge what arrives; they never walk into the kitchen and touch the stove themselves.

This layering is what makes suites survive an API changing shape: if an endpoint moves, you fix one client method, not fifty tests.
